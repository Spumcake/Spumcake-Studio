# Scaffold a sub-application

A sub-application is a separate program that owns one kind of creative work. The host finds it through its manifest, starts it, and draws what it declares through the protocol. This skill sets one up so that it follows those conventions from the first commit. It does not build the sub-application's features. Those come after, as ordinary work inside the scaffold.

Copy the template. Do not write a sub-application from scratch or from a description: `apps/template` is the smallest one that is known to work, and every new one starts as an exact copy of it.

## Choose the names

Names come from Studio's conventions guide, in the team repository at `.project/projects/spumcake-studio/documents/guides/conventions-guide.md`: a workspace is named for what it makes, and the one word for what it makes names its items and actions. A new workspace's names go into the guide, with the owner's yes, before it is scaffolded.

- **Id:** the name in lowercase, with hyphens between words, such as `storyboard-generator`. The folder `apps/<id>`, the crate name, the program name, and the manifest's `id` are all this value.
- **Name:** what people see, such as `Storyboard Generator`.
- **Word:** what it makes, such as storyboard. A new item is `protocol::free_name(&protocol::untitled("Storyboard"), taken)`: "Untitled Storyboard", then "Untitled Storyboard 2", free among its open tabs and the files in the project's folder.

Check that `apps/<id>` does not exist yet.

## Steps

1. Copy the folder `apps/template` to `apps/<id>`, with every file in it.
2. In `apps/<id>/Cargo.toml`, set the package `name` to the id. Leave the dependencies as they are: `protocol`, and `serde_json` for a tool's input schema and results.
3. In `apps/<id>/manifest.json`, set `id` and `executable` to the id and `name` to the name, and remove `hidden`: the template is hidden, and a new sub-application is not. Leave `protocol` as it is. When a sub-application is renamed later, its manifest's `formerly` lists its earlier ids, so the host gives it what was kept under them.
4. In `apps/<id>/src/main.rs`, set `TAB` to the id and the starting `label` to the new item's name. A scaffold keeps the contents message and the panel message, because the template declares the shared grid and the properties panel on the right. Remove one of those messages only when the task says this sub-application does not use it. Keep the template's tool group, which renames the tab, until the task gives the sub-application tools of its own; change its `name`, `description`, and `instructions` only to name the new sub-application's tab. Add no other messages.
5. In `apps/<id>/AGENTS.md`, change the heading to the name and replace the first paragraph with one sentence. If the task states what the sub-application is for, use that as the one sentence. If it does not, use: This sub-application is a scaffold copied from the template. Keep the rules unchanged.
6. Add `"apps/<id>"` to `members` in the workspace `Cargo.toml`.

## Check

- `cargo build` succeeds.
- `cargo run -p inpainter -- --app <id>` opens the Studio window with one tab labeled with the name, the empty toolbar, and only the shared components the sub-application declares. The host's common UI is all there: the tab strip with its menu button and plus, and the toolbar.
- With no host, `printf '{"type":"shutdown"}\n' | target/debug/<id>` prints the declaration, starting with `{"type":"hello","protocol":1}`, with a `tools` line before it ends with `{"type":"end"}`, and exits with status 0.
- With no host, `printf '{"type":"shutdown"}\n' | target/debug/<id> --restore` prints the declaration with no `tab`, `contents`, or `panel` line. Then `printf '{"type":"open"}\n{"type":"shutdown"}\n' | target/debug/<id> --restore` prints, after the declaration, the tab's `contents` and `panel`, then a `tabs` line listing it.
- With no host, `printf '{"type":"invoke","call":"c1","tab":"<id>","tool":"<id>__tab__rename_tab","input":{"label":"Renamed"},"group":"g1"}\n{"type":"shutdown"}\n' | target/debug/<id>` prints, after the declaration, a `tabs` line with the label Renamed, then `{"type":"result","call":"c1","ok":true,...}`.
- With no host, `printf '{"type":"ping"}\n{"type":"quit"}\n{"type":"shutdown"}\n' | target/debug/<id>` prints the declaration, then `{"type":"pong"}` and `{"type":"quit_ready"}`. The template answers both; a scaffold keeps those answers, or the host shows it as not responding and its window cannot close.

## What a scaffold does not include

No tools beyond renaming the tab, and no commands, menu rows, properties, documents, items, or saving. When the sub-application needs one of these, the work happens inside its own folder, and the host draws it only from what the sub-application declares. Never add a label, icon, control, or rule for one sub-application to the host.

## What a sub-application can declare later

After `end`, a sub-application can send these at any time; each replaces the one sent before. The types are in `protocol/src/declare.rs`, and the Storyboard Generator's `src/session/declare.rs` is a complete example.

- `tabs` — the tab list, the active tab, and the action the plus runs. A tab reported here and not in the greeting shows the contents and panel the greeting declared for the first tab.
- `keys`, `toolbar`, `menu`, `properties` — shortcuts, toolbar items, menu rows, and panel rows. Every control carries an `action`; when it is used the host sends `command {id, tab, arg}` with that action's id and argument, adding `value` to the argument when the control has one (a typed name, a slider's number, a sort position). A panel row's edit is `property {prop, value, preview}`. The Layers list's drag sends its `reorder` action with `{node, value}`, the position counted from the top among the row's siblings; a list that declares `nest` lets rows be dragged into and out of groups, and its `reorder` also carries `parent`, the group's id or null for the top level. The host never reads an action's id, except the drawing surface's own `canvas.zoom_in`, `canvas.zoom_out`, `canvas.fit`, and `canvas.zoom_to_selection`, and the window's `window.maximize`. A toolbar `popover` with an `action` is one split control: the icon sends `action`, and its chevron opens the rows; `selected` and `enabled` are as a button's. A Layers row may carry `detail`, a muted second line, `toggle_icon`, drawn in place of the eye, and `value`, words at its right.
- `properties` with `cell` — the panel's Prompt page: a `PanelCell` naming a cell the tab declared with `cells`, its `hint`, the `roles` a reference row's menu offers (`ReferenceRole {label, field, slot}`; a `slot` role is always its own row), the `reference_types` "Add reference" offers, rows `reference_menu` adds to each reference's menu, sent with the reference's index as `value`, the `settings` rows (`CellSetting {key, label, kind}`, `kind` as a panel row's), and `menu` for "…". The host draws the card after the page tabs and before the sections, and runs the cell.
- `contents {kind: "canvas"}`, `document`, and `canvas` — the drawing surface. The host previews each gesture from the declared tool and sends `gesture`, `select`, and `camera`; the sub-application commits and sends the whole `document` back.
- `contents {kind: "cells"}` and `cells {tab, cells, selected}` — a list of cells. The host draws every cell and runs every cell. The sub-application stores them. `run_cell {tab, cell}` and `stop_cell {tab, cell}` ask the host to run or stop one. The host sends `edit_cell` when a prompt is committed, `cell_result` when a run finishes, fails, or is stopped, `insert_cell` for a cell dragged in, and `select_cell` when one is selected. A cell's `kind` is a string. `text` and `image` are the kinds this version runs; an `image` cell's output is an image, a part `{path, media_type}` whose path is relative to the project. Any other kind is kept and drawn, and Run stays disabled. `running` is not a stored state. A run's `cell_result` names the `endpoint` and `model` it ran on, and its `effort` when one was set; keep all three with the run, so Run again repeats it. A tab of any contents kind may send `cells`, for the cells that make its items. A prompt may hold item parts, `{item, media_type, use?}`, which the host resolves into files when the cell runs; a cell may carry `settings`; and `cell_result` returns the `settings` it ran with and `used`, each item part with the fingerprint it resolved to: keep both with the run, since `used` is what the item it made was made from. The `video` kind, a prompt and its first and last frames in and a video out, and item parts run once the host's lifecycle work lands. A path or item part used as a reference may carry `role`, such as "Start frame, the keeper", and `field`, the model's input it fills. In a Skills project a cell may be a chain step, `step {chain, step}`: the step lives in `canon.sql` alone, so such a cell has empty `input`, `versions`, and `output`, and no `settings`, `endpoint`, or `model`, and a `cells` or `run_cell` that breaks this is refused when it is read, as `running` is. A cell without `step` is a draft, and an `edit_cell` from the Prompt page also carries its `settings`, `endpoint`, and `model`: keep them with the draft until its first run.
- `ask_assistant {text, items}` — put a prepared request, such as "use this take", in the conversation's composer with those items, for the user to send. It is not `ask`, the dialog question.
- `notices {tab, notices, corner}` — that tab's notice cards, replaced whole, in the `bottom_right` corner by default or `bottom_left`.
- `raster` with `film` — the filmstrip. `groups`, each `{label, count, menu}`, split `items` into labelled runs in order without changing their indices; a `FilmItem` may carry a `badge` such as "8.0 s", a `mark` such as the canon seal, `chosen`, and `pending`, `{state: "running", since?}` or `{state: "failed"}`, for a placeholder tile. A Ctrl- or Shift-click on a thumbnail sends `select` with `"extend": true` beside `value` (`Film::select_message`).
- `raster` with `camera_owner: "workspace"` — the workspace moves its own view. The host's camera then moves only when a view carries `camera`; the wheel, a pan, and the magnifier's click arrive as the gesture `view {zoom_by, pan_by, at}`, `at` and `pan_by` in image pixels, and the drawing surface's `canvas.zoom_in`, `canvas.zoom_out`, `canvas.fit`, and `canvas.zoom_to_selection` arrive as ordinary commands. The default, `host`, is as before.
- `contents {kind: "view3d"}` and `view3d {tab, scene, look, camera, reference, time, names, tool}` — a 3D view of a scene file, which the host reads and draws itself, as the scene contract's section 4 in the team repository sets out; geometry never crosses the protocol. `look` is `grey`, `coded`, or `simple`; `camera` is `{kind: "free", start?: {position, target, fov}}` or `{kind: "named", name}`, positions in the scene's metres with z up and `fov` horizontal, in degrees; `reference`, optional, is a published render the workspace decoded into a raw file, as a raster tab's `image`, with `width`, `height`, `show` (`{kind: "beside"}` or `{kind: "over", opacity}`), and `caption {view, reference}`, the words under each frame; `time` is seconds into the scene's animation; `names` shows objects' names; `tool` is `orbit` or `pan`. Each is replaced whole. The types are in `protocol/src/view3d.rs`.
- `open_report {request}` — show that request's report, `requests/<request>.html` in the project. Until the window draws reports, the host opens the page with the system's own opener.
- `file_resource {tab, path, from}` — ask the host's runner to file a plain file the workspace wrote in the project, such as a layer written out as a PNG, with `request.py resource <path>` and one `--from` per entry of `from`: the workspace's file in `work/` it came from first, then every linked file beneath it, so `touches` can follow an edit back to what it was painted on. The host keeps it for the runner, which acts on it with the lifecycle work.
- `timeline` — a row's `accepts` and an item's `kind` keep an item from being previewed as landing on a row that does not take its kind (`TimelineRow::takes`); an item's `earliest_start` and `latest_end` stop its edges there, such as at a sound's ends (`TimelineItem::limit_edge`). Refuse such a drop or edge in the model too.
- `ask` and `file` — a question or a file dialog. The host answers with `answer` or `file_result`.
- `quit_ready` after `quit`, and `pong` after `ping`.
- `tools {groups}` — what the assistant can do here, in tool groups, replacing the groups sent before. Send it with the declaration, before `end`, and again whenever the tools change. Each group has an `id`, a `name`, a `description`, `instructions` the assistant reads before using its tools (units, coordinates, what to read first, how ids work), and `tools`, each with a `name`, a `description`, `input`, a JSON Schema for an object, and optionally `implements`, the Spumcake-Skills skills it carries out. The host and the assistant know no tool group or tool by name: write these for a model that knows nothing else about the sub-application. A tool group is never a skill; a skill is an agent skill, a `SKILL.md`. The types are in `protocol/src/tools.rs`; the stored spelling `skills` still reads.
- `items {path, items}` — every item of one of its files: each piece of work inside it, with an `id`, a `name`, the `media_types` it can be rendered as, a `fingerprint` of its content made with `protocol::fingerprint`, or `protocol::cell_fingerprint` for a cell, and `made`, what it was made from. A sub-application with work in the project sends it for each of its files after `project`, and whenever a file's items change. The types are in `protocol/src/items.rs`, and the full lifecycle's `systems.md` in the team repository is the contract.
- `need {id, item, media_type}` and `pick {id, media_types}` — ask the host for another workspace's item as a file, answered by `provided`, or for the person to choose one, answered by `picked` with the item and which media type it is.
- `run_cell` with `content` and `at` — run a cell of a file no tab has open; the host's `cell_result` carries `at`.

## The assistant and the workspace

The host sends these; a sub-application that declares no tools never receives `invoke`.

- `invoke {call, tab, tool, input, group}` — run one tool on that tab. `tool` is `<application id>__<group id>__<tool name>`, made by `protocol::tool_key`. Carry it out through the same path the person's hand action takes, so undo, saving, and what the host shows are the same as for hand work. Send any `document`, `tabs`, or other message the call caused first, then `result {call, ok, output, images?}`: `output` is JSON for the model to read, such as what was made and its ids; with `ok: false` nothing changed and `output` says why; `images` holds PNG images in standard base64. Every change made under one `group`, the assistant's request, is one undo step, until another group or a change by hand. Undo and redo stay with the person, so they are never tools.
- `open {path?}` — open that file in a new tab or, with no path, the tab the sub-application opens of its own at start. A tab opened this way is declared as the greeting declares tabs: send its `contents` and, when it uses the panel, its `panel`, before the `tabs` that lists it.
- `claim {id, path}` — say whether this file is the application's own work. Answer `claimed {id, yours}`. The host asks the application that opened the dialog first, then the others. The first that claims it receives `open`. A file nobody claims goes to the application that asked, which reports its own error. The host never reads the file to decide.
- `render {id, item, media_type, use?}` — write that item of one of its files as a file of `media_type` at `protocol::render_path`, which keeps a cell's prompt and result apart, and answer `rendered {id, path, fingerprint}`, with the item's fingerprint as declared in `items`, or `rendered {id, error}`. A sub-application that declares no items yet answers `protocol::no_items(id)`, as the template does.
- `shown {tab, revision, at}` — the host drew that revision of the tab's stage or raster image, at `at`, milliseconds since the Unix epoch, once per revision. Only a workspace playing sound against its frames needs it. It is not the person's input: never let it end an undo group or reset a wait for quiet, such as a write that waits for 250 ms with no message, or a workspace that sends an image after each message never goes idle.
- `stale {path, items}` — which of that file's items are out of date, and which items they were made from changed; show it as the approved views do.
- `view3d_camera {tab, position, target, fov}` — the user stopped turning that 3D view's free camera, here. Keep it, so the view starts there again.
- `view3d_picked {tab, object, label}` — the user pointed at an object in that 3D view: its node's name, and its label group's key, empty when it has none.
- `cell_became_step {tab, cell, step}` — in a Skills project, that draft cell is now the chain step `step {chain, step}`: keep only the pointer, with empty `input`, `versions`, and `output`, and no `settings`, `endpoint`, or `model`, as for any step's cell.
- `takes {cell, rounds}` — in a Skills project, every round that cell made, read from `requests/` and the pending records, in place of `cell_result`: each `Round` has its `request`, `number`, `model`, the `prompt` and `references` as sent, `left_out`, its `state` (`running`, `pending`, `done`, `failed`, or `cancelled`), `started`, `count` while running, its `takes`, each `{path, media_type, canon}`, `error`, and `report`. Show them on the filmstrip; never store them.
- `preview {id, path, media_type}` — sent to a workspace whose `edits` covers the media type: answer `previewed {id, thumbnail?, badge, cues, error?}`, with `cues`, each `{at, label}` in seconds, for a sound. A workspace that cannot answers with `error`.
- `keep {tab}` — make sure that tab's file is written. Answer `kept {tab, path?, error?}`: `path` with no `error` when written, no `path` and no `error` when clean or untouched, and `error` when writing failed.
- Each `tabs` entry carries `path`, the file the tab shows once it has one, and `saves`, whether the tab is a document that can be saved to a file. The template's tab does not save.
- Started with `--restore` (`protocol::RESTORE_FLAG`), a sub-application opens no document of its own: its greeting has no `tab`, `contents`, or `panel`, and it waits for `open`. The host uses this to reopen a workspace.
- `project {folder, skills}` — the current project's folder as an absolute path, sent before any `open`; `skills` is true for a Skills project, whose requests run through Spumcake-Skills' scripts. Inside a project a sub-application that saves documents:
  - writes each document into that folder by itself, about a second after it changes, with no Save, Save As, or save question; the Storyboard Generator and Recipe Creation show how, with a loop that also wakes with no message;
  - names a new document's file after its tab, which is named by the conventions guide's rule, free among the folder's files, and never replaces another file;
  - writes everything before a tab closes, before `kept`, and before `quit_ready`, so closing and quitting ask nothing;
  - refuses every path outside the folder, from `open`, `file_result`, `claim`, and its own recent files, and opens nothing in its place.

  The host asks before a file from outside comes in, and sends only the imported copy's path.

The host starts each sub-application with `--data-dir <folder>`, its own folder inside Studio's data folder, for its preferences and recovery files.

## When the protocol cannot say something

The protocol in `protocol/` is the only way the host and a sub-application talk, and its source is the reference for every message. When a sub-application needs something the protocol cannot express, extend the protocol, teach the host to draw or handle it, and update this skill, all in the same change. Raise `PROTOCOL_VERSION` when an existing message changes meaning. Change the template only when every sub-application needs the change; it stays the smallest one that works. Do not work around the protocol with a side channel, a shared file, an environment variable, or a special case in the host.

## Bringing an existing program in

Scaffold first, so the host already shows the new sub-application's tab. Then, before writing code, map what carries over from the existing program: each file, function, constant, and resource it needs, and where it lands. Carry code over unchanged, or with named edits that the new structure requires. Live drawing, which the host does with its shared drawing code, is separated from the document, saving, and undo, which stay with the sub-application. Do not rewrite what the existing program already does.

## Finish

Report the id and name, the files created or changed, and the result of each check.
